# Tibo 全部新动态的中文微信通知

本部署将 Tibo（`@thsottiaux`）自己发布的全部新帖子和回复推送到个人微信，不再只匹配 reset。邮件已按用户要求关闭：工作流设置 `EMAIL_ENABLED=false`，不再注入邮件凭据，也没有测试邮件入口；旧队列中的待发邮件会取消，其他渠道的待发记录保留。原项目的邮件能力仍可由其他部署显式配置使用。

## 通知内容

- 标题标注“原创帖”或“回复”以及发帖的北京时间。分类使用数据源的回复关系字段，不根据正文开头是否包含 `@` 猜测；旧记录或缺失元数据时显示“类型待确认”。引用他人帖子的独立发帖归入原创帖，转发他人的内容仍按上游来源规则排除。
- 回复显示被回复的账号和原帖链接（来源提供时）。
- 正文包含中文译文、英文原文、原帖链接，以及精确到秒的发帖时间、推送时间和发帖至推送的间隔。日期和时间均使用北京时间；推送时间指生成并提交该次通知的时间，手机实际接收还受平台投递影响。
- 图片以远程 HTTPS 图片引用展示，不分析或翻译图片中的文字。超长微信正文会明确标注为节选，并保留完整原帖链接。

仅新增关系元数据或调整通知样式不会更改帖子版本，因而不会重新通知已处理的历史动态。

## GitHub Actions Secret 与个人绑定

1. 在 [PushPlus 官网](https://www.pushplus.plus/login.html) 用自己的微信扫码登录，完成实名认证，并关注或绑定公众号。实名信息仅在官网填写。
2. 将“一对一消息”页面自己的用户或消息令牌直接添加为仓库 Actions Secret `PUSHPLUS_TOKEN`，不要粘贴到聊天、源码、Issue 或日志。不填则不启用微信渠道。
3. 运行工作流“Tibo 中文微信通知”，勾选微信测试选项。到 PushPlus 历史消息核对内容和发送记录，再确认手机微信收到通知。

微信使用 HTTPS POST，将令牌放在请求体中；不设置群组或好友收件人，只发给令牌所属用户。令牌本身不进入监测状态，仅保存目标身份的哈希。翻译仅向 Google Translate 网页翻译接口传输公开帖子正文。翻译入口和 FxEmbed 均为第三方依赖。

## 时间、额度与失败重试

默认每五分钟检查一次，避开整点启动。GitHub Actions 不保证准点触发，高峰期可能延迟或丢弃调度，数据源也可能缓存结果，因此不能保证五分钟内或秒级通知。工作流按操作系统、CPU 架构、Node 主版本和依赖锁文件缓存已安装依赖；精确命中时跳过重复安装，以缩短取得运行器后的启动等待，首次运行及依赖变化时仍完整安装。

免费实名用户的微信额度目前为每日约200次请求、每分钟5次，以 [官方额度说明](https://www.pushplus.plus/doc/guide/use.html) 为准。程序每个滚动61秒窗口最多尝试4次，达到频率限制时在本次运行内等待并继续发送，普通积压不再依赖下一次定时触发。为控制单次任务时长，超过20次请求的余量仍留在持久化队列。请求时间点以无秘密的 `pushplus-rate.json` 保存，重启或接着发送测试消息时继续遵守限流。失败请求同样计入限流；超过每日额度后不能保证当天全部动态通过微信送达。

2026-10-25 实际出现了超过3小时没有 GitHub 自动触发的空档，原生 schedule 不能作为及时提醒的唯一依据。独立 Cloudflare 定时触发的个人配置见 [部署说明](../workers/personal-scheduler/README.zh-CN.md)，其部署与授权状态以该说明及云端实际运行记录为准。

PushPlus 的 `code=200` 和流水号只表示服务端已接受请求，不能证明微信已送达；最终状态需在官网记录或微信端核对。当前队列在收到有效受理回执后记为该渠道完成，不自动查询异步投递状态。接口拒绝、网络或翻译失败则保留待重试记录。

读取和发送断点持久化到独立 `monitor-state` 分支，收到每个目标的受理回执后保存状态。投递状态不明、或受理后 GitHub 状态未成功保存时可能重复通知。首次监测只建立最新游标；新增微信目标只接收启用后新入队的动态，不自动补发之前已完成的通知。
